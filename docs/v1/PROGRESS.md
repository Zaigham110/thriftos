The sort screen learned the lot's weight only from the sort queue (which the service worker may serve from its 5-minute cache, made before the lot existed) or from the first summary (which can fail on a slow connection); with neither, the weight stayed 0, "Close lot" skipped the question and the total showed 0.0 kg. ## Decisions
- Super admin BILLING is a module of the `SYSTEM` business, so plans and billing are off on every install until the platform owner turns them on in the database.
- "Owner home < 2 s" is measured on the installed app (service worker and the owner's last numbers on the phone), which is how an owner opens it every day; the first-ever visit is measured separately (7.7 s on Slow 3G + 4× CPU).
- `NG_BUILD_OPTIMIZE_CHUNKS` is an experimental Angular build option; all browser tests pass with it. If a future Angular drops it, the build still works, only the first visit gets slower.
- Demo profit per kg is realised profit over all kg bought (only ~10% of each container is baled and sold in the story), so the numbers are small (Rs 14–30); the comparison between countries is the point. The demo script says so.
- The setup wizard asks business name, currency and language on one screen (3 fields), then one question per screen; categories are chips (tap to remove) rather than a list editor.
- Karachi template categories (`server/src/tenant/setup-template.ts`) are a first guess in floor words; the owner edits them in the wizard. To be checked with real traders.
- A munshi's phone is unique across all businesses so sign-in needs only phone + PIN (no business code). A munshi working for two businesses needs two numbers — rare enough for v1.
- PIN lock: 5 wrong in a row → 15 minutes; the owner can unlock or set a new PIN at once.
- Owner home shows exactly 3 numbers + today's sales (owner's call); the supplier/country comparison and the container list from doc 02 live behind "Profit per container".
- "Profit per container" is the average realised profit of the last 5 containers (sold lines only); unsold stock is not counted as profit.
- Sort lines are confirmed when stored on the phone (not after the server answers): on Slow 3G a line otherwise takes 11 s. The keypad already refuses more than is left, and a later refusal shows under Needs attention.
- Tapping Undo takes back the line its toast names; a toast is replaced only when the next line is stored.
- The dev-DB hook also blocks commands whose text merely contains a reset/migrate (e.g. a heredoc writing a script); write such files with the editor instead. Accepted: false positives are cheap, a missed dev-DB reset is not.
- Test DB lives on the same Postgres server as dev, named `<db>_test`; never the dev DB.
- Frontend has no specs yet, so CI only typechecks and builds it; frontend unit tests are added with the services they cover (offline queue, i18n).

- Making a bale is one step (no draft) because journey 3 has none; manual stock picking is the optional `allocations` field.
- Bale codes: new bales are `B-0001`… per tenant (3.5); bales made before keep `TENANT-CAT-GRADE-YYYYMMDD-NNNN`.
- Sort/grade cost split is still plain proportional Decimal; largest-remainder rounding arrives with `costing/` in task 1.2.
- Open question for Phase 1/2: tenants with `sortingStages = 1` have no grade outputs, so bales must also be makeable from category outputs (`RepackInputAllocation.gradingOutputId` is required today).
- Super-admin area (`/admin`) keeps its own layout (`shared/ui/app-shell-layout` via `admin-shell`): it is the platform operator's console, not the tenant app.
- Tab visibility still uses the old `operationalModules` values (INTAKE, SORTING, ...); switches to `enabledModules` (RECEIVE, SORT, ...) with the Tenant migration in 1.1. Tenant policy fields (capture/guidance/connectivity) are still read by flow receive/control/offline-draft and are removed with that migration.
- Found: the base seed creates no waste categories, so a lot with a remainder cannot be closed. Journey 2 needs the waste tile always present: the setup wizard (3.8) and demo seed (4.1) must always create a default "Waste/Katran" type.
- Bale take cost is the cumulative share of the source output (`cost(usedAfter) − cost(usedBefore)`), not `kg × rounded rate`, so bales from an output always add up to the output's cost to the paisa.
- A purchase in PKR ignores fxRate; old containers become PKR purchases so their totals are unchanged.
- Default waste type is ensured by name ("Waste/Katran") everywhere, because tenant bootstrap already creates "<category> Waste" types.
- Container lots keep their old (net-weight) allocated costs until recalculated; task 1.3 adds the recompute command to run once after applying the migrations.
- ts-jest runs with `isolatedModules: false` (tests are type-checked; needed for honest coverage of Nest services). Full suite ≈ 45 s.
- `src/costing/recompute.ts` is a command-line entry point and is excluded from the coverage gate; it is exercised by the migration rehearsal.
- Lot corrections use the existing `rag.create` permission (there is no `rag.update`).
- Customer, sale and khata endpoints need a tenant login but no specific permission (as the sales endpoints already did); roles for munshi vs owner come with phone + PIN login (3.7).
- The old credit-limit check on issuing a sale is dropped with the draft sale flow (2.3); credit limits stay as optional data only.
- One e2e run (of ~10) during 2.3 showed 6 failures that did not reproduce in any later run; noted here in case it returns.
- Server-side enforcement of `enabledModules` (doc 03 rule 6): built in 4.5 for the advanced modules; the five v1 modules are still only hidden in the app (turning SORT off is a setting for traders, not a permission).
